# 1. PROGRAM OVERVIEW

**Program Name:** Robotics & Physical Computing  
**Category:** Core Solution  
**Duration:** 14 weeks (one school term)  
**Weekly Contact Time:** Minimum 2 hours per week

## Program Description

STEMForge Robotics & Physical Computing is a hands-on engineering program built from first principles. Students program microcontrollers, integrate sensors, design mechanical systems, and build autonomous robots. Every student finishes the term with a functioning autonomous robot that they designed, built, programmed, tested, documented, and presented — not a preassembled kit.

The program operates as one progressive engineering project: the **STEMForge Navigator**, an autonomous campus-assistant robot capable of obstacle avoidance, line-following navigation, and payload delivery. Students construct this robot subsystem by subsystem across 14 weeks, experiencing the full engineering design cycle repeatedly.

## Why the STEMForge Navigator?

The final robot was selected because it:
- Is achievable within 14 weeks for beginners
- Demonstrates meaningful engineering (sensor fusion, decision logic, mechanical design)
- Connects to real Kenyan applications: campus logistics, smart agriculture, hospital delivery, warehouse automation
- Requires all 12 target competencies
- Can be built with low-cost, locally available components
- Allows clear differentiation between basic, advanced, and expert implementations

# 2. PROGRAM PHILOSOPHY

STEMForge does not teach robotics by having students follow step-by-step instructions to assemble kits. We teach engineering by having students **think, design, fail, debug, and improve**.

## Core Principles

1. **First Principles First:** Every concept is built from foundational understanding. We do not ask students to copy code they do not understand.
2. **Project-Based Progression:** The entire 14 weeks serve one engineering project. Each week adds a subsystem to the final robot.
3. **Learn → Build → Test → Fail → Debug → Improve → Integrate → Demonstrate:** This cycle repeats every week.
4. **Engineering Design Process:** Students experience the full cycle — Identify, Research, Generate Ideas, Design, Build, Test, Analyze, Improve, Document, Present — not once, but repeatedly.
5. **Hands-On Dominance:** 60–70% of every session involves active building, wiring, programming, testing, measuring, or debugging.
6. **Kenyan Relevance:** Engineering is connected to local challenges — agriculture, transport, environmental monitoring, manufacturing, and ICT entrepreneurship.
7. **Differentiated Learning:** Every practical offers three challenge levels so all students are stretched appropriately.
8. **Documentation as Engineering Practice:** Students maintain an engineering notebook from Day 1. Documentation is not an afterthought; it is part of the engineering process.

## Teaching Approach

The STEMForge facilitator acts as a **guide and engineering mentor**, not a lecturer. Students are asked:
- What do you think will happen?
- Why did it happen?
- How can you test your assumption?
- What failed?
- How would you improve the design?
- How could this technology solve a real problem in your community?

## PHASE 1: ELECTRONICS & CIRCUITS (Weeks 1–3)

---

## WEEK 1 — Foundations of Electricity & Safe Circuit Building

### 1. Theme
Electrical safety, fundamental electrical quantities, and constructing first circuits.

### 2. Learning Objectives
By the end of Week 1, students will be able to:
1. Identify common electronic components (resistors, LEDs, breadboards, jumper wires) by sight and function.
2. Explain the relationship between voltage, current, and resistance using Ohm's Law (V = I × R).
3. Calculate the correct resistor value for protecting an LED in a simple circuit.
4. Construct a complete circuit on a breadboard powering an LED from a battery.
5. Demonstrate safe handling of electrical components and batteries.

### 3. Concepts & Theory

**Electricity as Flow:** Electricity is the flow of electrons through a conductor, similar to water flowing through a pipe. Voltage is the pressure pushing electrons, current is the rate of flow, and resistance opposes the flow.

**Ohm's Law:** V = I × R, where V is voltage (Volts), I is current (Amperes), and R is resistance (Ohms). If you know two values, you can calculate the third.

**LED Protection:** LEDs are diodes that emit light when current flows in one direction. They have low internal resistance, so a series resistor is required to limit current and prevent burnout.

**Breadboards:** Breadboards are reusable prototyping platforms. The central groove separates two halves. Rows are connected horizontally (5 holes per row), and power rails run vertically along the edges.

**Component Polarity:** LEDs have a longer leg (anode, positive) and shorter leg (cathode, negative). Resistors are non-polarized. Batteries have positive (+) and negative (−) terminals.

### 4. Components & Equipment
- Arduino Uno (1 per student — for familiarization only, not programming)
- Breadboard (half-size, 400 tie points)
- Jumper wires (male-to-male, assorted lengths)
- 5mm LEDs (red, green, yellow — 3 per student)
- Resistors (220Ω, 1kΩ, 10kΩ — assorted pack)
- 9V battery with snap connector OR 4×AA battery holder
- Multimeter (1 per 2 students)
- Component reference sheet
- Engineering notebook (A4 hardcover or spiral-bound)

### 5. Pre-Lab / Starter Activity (10 minutes)
**"The Human Circuit"**
Students stand in a circle holding hands. One student holds a battery (represented by a labeled card), another holds an LED. The facilitator explains that the circle represents a closed circuit — current can flow. When two students break hands (open the switch), the "LED" stops working. This kinaesthetic activity introduces the concept of a closed loop.

### 6. Instructor Teaching (20 minutes)
1. **Safety First (5 min):** Never short-circuit batteries. Do not touch exposed metal when power is on. Report damaged components immediately. Keep water away from electronics.
2. **Component Introduction (5 min):** Show each component. Explain resistor color codes (4-band). Demonstrate LED polarity.
3. **Breadboard Anatomy (5 min):** Draw the breadboard on the board. Show which holes are connected. Emphasize the central divide.
4. **Ohm's Law (5 min):** Work through one calculation: a red LED (Vf = 2V) on a 9V battery needs R = (9−2)/0.02 = 350Ω. Show how 220Ω or 470Ω resistors are chosen in practice.

### 7. Hands-On Practical (50 minutes)

**Objective:** Build a breadboard circuit that lights an LED when a push button is pressed.

**Materials:** Breadboard, LED, 220Ω resistor, push button, jumper wires, battery.

**Procedure:**
1. Place the push button across the central groove of the breadboard.
2. Connect the positive power rail to one side of the button.
3. Connect the other side of the button to the resistor.
4. Connect the resistor to the LED anode (longer leg).
5. Connect the LED cathode to the negative power rail.
6. Connect the battery. Press the button. The LED should light.
7. Use the multimeter to measure voltage across the LED and across the resistor.
8. Verify that V_LED + V_Resistor ≈ V_Battery.

**Expected Result:** LED lights when button is pressed. Multimeter readings confirm Ohm's Law.

**Troubleshooting:**
- LED doesn't light → Check polarity (flip LED). Check battery voltage. Check breadboard connections.
- LED very dim → Resistor too large. Try 220Ω instead of 1kΩ.
- LED burns out → Resistor missing or too small. Replace LED and add resistor.

**Extension Challenge:** Build a circuit with TWO LEDs (red and green) where pressing the button lights red, releasing lights green (hint: use the button's NC/NO properties or two buttons).

### 8. Engineering Challenge
"Design a circuit that acts as a simple battery tester: an LED should light brightly when the battery is fresh (9V), dimly when partially drained, and not light when the battery is dead. Select the appropriate resistor and explain your reasoning using Ohm's Law."

### 9. Student Deliverable
- Working LED circuit on breadboard
- Multimeter measurement sheet showing V, I, and R for two different resistor values
- Engineering notebook entry with circuit diagram (hand-drawn), component list, and reflection

### 10. Assessment
- **Practical (60%):** Circuit functions correctly; measurements are accurate.
- **Quiz (30%):** 5 questions on Ohm's Law, component identification, and breadboard connections.
- **Notebook (10%):** Clear circuit diagram, labeled components, and reflection.

### 11. Safety
- Do not short 9V batteries — they can overheat.
- LEDs can become warm during prolonged use.
- Report any damaged jumper wires or battery connectors.
- Keep workspace organized to prevent accidental short circuits.

### 12. STEM / Engineering Connection
This week's concepts underpin all modern electronics — from mobile phones to medical devices. In Kenya, understanding basic electronics enables repair of agricultural sensors, solar lighting systems, and hospital equipment. Electrical safety is critical for anyone working with solar installations or generator maintenance.

### 13. Competencies Developed
- Competency 2: Electronics & Circuit Construction
- Competency 11: Technical Documentation

## WEEK 2 — Series, Parallel, Measurement & Troubleshooting

### 1. Theme
Circuit topology, measurement, and systematic fault diagnosis.

### 2. Learning Objectives
By the end of Week 2, students will be able to:
1. Explain the difference between series and parallel circuits using the water-flow analogy.
2. Calculate total resistance in series and parallel resistor networks.
3. Use a multimeter to measure voltage, current, and resistance in a live circuit.
4. Construct series and parallel LED circuits and predict behavior before building.
5. Apply a systematic troubleshooting process to identify and repair circuit faults.

### 3. Concepts & Theory

**Series Circuits:** Components are connected end-to-end. Current is the same through all components. Total resistance R_total = R1 + R2 + R3. If one component fails, the entire circuit stops.

**Parallel Circuits:** Components are connected across the same two points. Voltage is the same across all branches. Total resistance is calculated by: 1/R_total = 1/R1 + 1/R2 + 1/R3. If one branch fails, others continue.

**Multimeter Usage:**
- **Voltage (V):** Meter in parallel with the component.
- **Current (A):** Meter in series with the circuit (break the circuit and insert the meter).
- **Resistance (Ω):** Component removed from circuit; meter across component only.

**Troubleshooting Process:**
1. Observe symptoms (what is happening vs. what should happen)
2. Hypothesize possible causes
3. Isolate the fault (divide and conquer)
4. Test the hypothesis
5. Repair and verify
6. Document the fault and solution

### 4. Components & Equipment
- Breadboard and jumper wires
- LEDs (3 per student)
- Resistors (220Ω, 470Ω, 1kΩ — multiple)
- Potentiometer (10kΩ linear)
- Multimeter
- 9V battery or 4×AA holder
- "Mystery circuit" cards (pre-built faulty circuits for troubleshooting practice)

### 5. Pre-Lab / Starter Activity (10 minutes)
**"Predict Before Build"**
The facilitator shows a series circuit diagram with two LEDs and one resistor. Students vote: Will both LEDs light? Will they be equally bright? Will one be brighter? Students write predictions in their notebooks, then build to verify.

### 6. Instructor Teaching (20 minutes)
1. **Series vs. Parallel (8 min):** Draw both topologies. Calculate examples. Show that parallel branches draw more total current.
2. **Multimeter Demonstration (7 min):** Live demo measuring voltage across a resistor, current through a branch, and resistance of a disconnected component. Emphasize: NEVER measure resistance in a live circuit.
3. **Troubleshooting Framework (5 min):** Introduce the 6-step process. Show a deliberately faulty circuit and model the thinking process aloud.

### 7. Hands-On Practical (50 minutes)

**Objective:** Build a dual-brightness night-light circuit using a potentiometer to control LED brightness, then measure and verify behavior.

**Materials:** Breadboard, 2× LEDs (different colors), 220Ω resistor, 10kΩ potentiometer, jumper wires, battery, multimeter.

**Procedure:**
1. Build a series circuit: Battery → Potentiometer → Resistor → LED → Ground.
2. Turn the potentiometer knob. Observe LED brightness changes.
3. Measure voltage across the potentiometer at minimum and maximum brightness settings.
4. Measure voltage across the LED at both settings.
5. Verify: V_battery = V_pot + V_resistor + V_LED (within measurement error).
6. Replace the single LED with two LEDs in parallel (each with its own 220Ω resistor).
7. Observe: Does the potentiometer still control both? Measure current in each branch.

**Expected Result:** Potentiometer dims/brightens LED(s). Voltage measurements confirm conservation of energy. Parallel LEDs behave independently.

**Troubleshooting:**
- Potentiometer has no effect → Wired as fixed resistor (using only two legs). Use all three legs.
- LEDs too dim even at maximum → Total resistance too high. Check resistor value.
- One LED in parallel doesn't light → That branch has an open circuit or reversed LED.

**Extension Challenge:** Build a circuit where three LEDs indicate battery level: green (full), yellow (medium), red (low). Use a voltage divider with resistors. Calculate resistor values so each LED turns on at a different threshold.

### 8. Engineering Challenge
"A solar garden light in your village has stopped working. The LED doesn't light at night. Using your multimeter and troubleshooting process, design a diagnostic procedure to identify whether the fault is in the solar panel, battery, LED, or resistor. Write your step-by-step diagnosis plan before touching any components."

### 9. Student Deliverable
- Working potentiometer-controlled circuit
- Measurement table with predicted vs. measured values
- Troubleshooting log documenting one fault they intentionally introduced and then fixed
- Engineering notebook entry with series/parallel comparison diagram

### 10. Assessment
- **Practical (50%):** Correct circuit construction; accurate measurements.
- **Troubleshooting Task (30%):** Successfully diagnose and repair a "mystery circuit" within 10 minutes.
- **Quiz (20%):** Series/parallel calculations and multimeter safety.

### 11. Safety
- Current measurement requires breaking the circuit. NEVER connect ammeter in parallel — it will short-circuit.
- Potentiometers can overheat if too much current passes through them. Stay within component ratings.
- Always disconnect power before changing circuit configuration.

### 12. STEM / Engineering Connection
Series and parallel circuits are everywhere: Christmas lights (series historically, parallel modern), household wiring (parallel), battery packs (series for voltage, parallel for capacity). In Kenya, understanding these topologies is essential for designing solar home systems, repairing motorcycle electronics, and building irrigation sensors.

## WEEK 3 — Sensors, Input Systems & First Automation

### 1. Theme
Transducing physical quantities into electrical signals and building responsive systems.

### 2. Learning Objectives
By the end of Week 3, students will be able to:
1. Explain how a sensor converts a physical quantity into an electrical signal.
2. Construct a voltage divider circuit using an LDR (Light Dependent Resistor) and a fixed resistor.
3. Program an Arduino to read analog input from a sensor and respond with an output.
4. Build a system that automatically responds to environmental changes (light level).
5. Calibrate a sensor by mapping raw values to meaningful ranges.

### 3. Concepts & Theory

**Sensors as Transducers:** A sensor converts a physical property (light, temperature, distance, motion) into an electrical signal (usually voltage or resistance change) that a microcontroller can read.

**Voltage Dividers:** Two resistors in series divide the input voltage. V_out = V_in × (R2 / (R1 + R2)). If one resistor is a sensor (like an LDR whose resistance changes with light), V_out changes with the physical quantity.

**Analog vs. Digital:** Digital signals have two states (HIGH/LOW, 1/0). Analog signals have a continuous range. The Arduino's Analog-to-Digital Converter (ADC) reads voltages between 0V and 5V and converts them to numbers from 0 to 1023.

**Arduino Analog Input:** `analogRead(pin)` returns 0–1023. On a 5V Arduino, 0 = 0V and 1023 = 5V. Each step ≈ 0.0049V (4.9mV).

**Calibration:** Sensors rarely output exact units. Calibration means reading the sensor in known conditions (e.g., bright light and darkness) and mapping those raw values to meaningful ranges.

### 4. Components & Equipment
- Arduino Uno + USB cable
- Breadboard and jumper wires
- LDR (Light Dependent Resistor, 2 per student)
- 10kΩ resistor
- LED (red, green, yellow)
- 220Ω resistors
- Potentiometer (10kΩ)
- Multimeter
- Flashlight or phone torch (for testing)
- Laptop with Arduino IDE installed

### 5. Pre-Lab / Starter Activity (10 minutes)
**"Sensor Hunt"**
Students list as many sensors as they can find in the classroom or on their person in 3 minutes (phone touchscreen, light sensor, temperature sensor, microphone). Discuss: What physical quantity does each measure? What does it output?

### 6. Instructor Teaching (20 minutes)
1. **Sensor Fundamentals (5 min):** Define transducer. Show LDR in bright light (low resistance, ~1kΩ) and darkness (high resistance, ~1MΩ).
2. **Voltage Divider Theory (5 min):** Draw circuit. Calculate V_out for R_LDR = 1kΩ and 100kΩ with 10kΩ fixed resistor. Show that V_out changes significantly.
3. **Arduino Analog Input (5 min):** Explain ADC. Show `analogRead()` code. Demonstrate Serial Monitor output.
4. **Calibration Concept (5 min):** Show how the same LDR gives different raw values under different lights. Calibration makes the sensor useful.

### 7. Hands-On Practical (50 minutes)

**Objective:** Build an automatic night-light that turns on an LED when ambient light drops below a threshold.

**Materials:** Arduino, breadboard, LDR, 10kΩ resistor, LED, 220Ω resistor, jumper wires.

**Procedure:**
1. Build the voltage divider: 5V → LDR → 10kΩ resistor → GND. Connect the junction to Arduino A0.
2. Connect LED with 220Ω resistor to Arduino pin 9.
3. Open Arduino IDE. Write the program with analogRead, threshold comparison, and digitalWrite.
4. Upload the code. Open Serial Monitor. Cover the LDR and expose it to light. Record the values.
5. Set the threshold halfway between the bright and dark readings.
6. Test: Cover the LDR → LED turns on. Expose to light → LED turns off.
7. Add a second LED (green) that turns on in bright light, creating a dual-indicator system.

**Expected Result:** LED automatically responds to light level. Serial Monitor shows changing values. Threshold is calibrated to the room's conditions.

**Troubleshooting:**
- Serial Monitor shows 0 or 1023 constantly → LDR wired incorrectly or wrong pin.
- LED doesn't respond → Check pin number in code vs. wiring. Check LED polarity.
- Values don't change much → Fixed resistor poorly chosen. Try 1kΩ or 100kΩ.

**Extension Challenge:** Add a potentiometer to allow the user to adjust the threshold in real-time without reprogramming. Read the potentiometer on A1 and use that value as the threshold.

### 8. Engineering Challenge
"Design an automatic irrigation indicator for a Kenyan farm. The system should use an LDR to detect daylight (plants only need water during the day) and a soil moisture sensor (represented by a second variable resistor) to detect dry soil. The system should light a red LED only when BOTH conditions are met: it is daytime AND the soil is dry. Write the logic before wiring."

### 9. Student Deliverable
- Working automatic night-light with calibrated threshold
- Arduino program with comments explaining each line
- Serial Monitor screenshot or recorded values
- Engineering notebook entry with voltage divider calculation, calibration table, and logic flow diagram

### 10. Assessment
- **Practical (50%):** Sensor circuit works; calibration is appropriate; LED responds correctly.
- **Code Review (30%):** Code is commented, logically structured, and uses meaningful variable names.
- **Engineering Challenge (20%):** Logical design for irrigation indicator; correct use of AND conditions.

### 11. Safety
- Arduino pins can supply only 40mA maximum. Do not connect low-resistance loads directly.
- Always disconnect USB/power before rewiring.
- LDRs are fragile. Handle by the leads, not the glass face.

### 12. STEM / Engineering Connection
Sensors are the eyes and ears of automation. In smart agriculture, light sensors control greenhouse ventilation. In security systems, LDRs detect tampering. In environmental monitoring, sensors track deforestation by measuring light penetration. Kenya's push for precision agriculture depends on students mastering these fundamentals.

## WEEK 4 — Arduino Foundations: Digital World

### 1. Theme
Microcontroller architecture, digital input/output, and the structure of embedded programs.

### 2. Learning Objectives
By the end of Week 4, students will be able to:
1. Explain the function of a microcontroller as a small computer that reads inputs, processes logic, and controls outputs.
2. Navigate the Arduino IDE: write, verify, and upload code to an Arduino Uno.
3. Use `pinMode()`, `digitalWrite()`, and `digitalRead()` to control and sense digital pins.
4. Write a complete Arduino program with proper `setup()` and `loop()` structure.
5. Build a digital input/output system using push buttons and LEDs.

### 3. Concepts & Theory

**What is a Microcontroller?** A microcontroller is a complete computer on a single chip: CPU, memory (RAM and flash), and I/O ports. The Arduino Uno uses the ATmega328P microcontroller. Unlike a laptop, it has no screen or keyboard — it interacts with the world through sensors and actuators.

**Arduino Program Structure:**
- `setup()`: Runs once when the Arduino starts. Used to configure pins, start serial communication, initialize variables.
- `loop()`: Runs repeatedly forever. This is where the main logic lives.

**Digital Pins:** Pins 0–13 on the Arduino Uno can be configured as INPUT or OUTPUT. Digital means two states: HIGH (5V) or LOW (0V).

**Pull-Up and Pull-Down Resistors:** A floating input pin (not connected to anything) picks up electrical noise and gives random readings. A pull-down resistor (10kΩ to GND) ensures the pin reads LOW when the button is not pressed. A pull-up resistor (10kΩ to 5V) ensures HIGH when not pressed. Arduino has internal pull-ups: `pinMode(pin, INPUT_PULLUP)`.

**Serial Communication:** The Arduino can send text back to the computer via USB. `Serial.begin(9600)` starts communication. `Serial.println()` sends text. The Serial Monitor in Arduino IDE displays it.

### 4. Components & Equipment
- Arduino Uno + USB cable
- Breadboard and jumper wires
- LEDs (3) with 220Ω resistors
- Push buttons (2)
- 10kΩ resistors (for pull-down)
- Laptop with Arduino IDE

### 5. Pre-Lab / Starter Activity (10 minutes)
**"The Arduino is a Brain"**
Students label a diagram of the Arduino: "brain" (microcontroller), "senses" (input pins), "muscles" (output pins), "memory" (RAM), "habits" (flash/program memory). This builds the mental model before touching code.

### 6. Instructor Teaching (20 minutes)
1. **Arduino Tour (5 min):** Show the board. Point out power pins, digital pins, analog pins, USB port, reset button, TX/RX LEDs.
2. **IDE Walkthrough (5 min):** Open Arduino IDE. Show verify, upload, Serial Monitor. Explain the code editor, message area, and board selection.
3. **Blink Program (5 min):** Live-code the classic Blink sketch. Explain every line. Upload and demonstrate.
4. **Digital Input (5 min):** Show button wiring with pull-down resistor. Explain why the resistor is essential. Show `digitalRead()`.

### 7. Hands-On Practical (50 minutes)

**Objective:** Build a traffic-light controller with a pedestrian crossing button.

**Materials:** Arduino, breadboard, red/yellow/green LEDs with resistors, push button, 10kΩ resistor, jumper wires.

**Procedure:**
1. Wire three LEDs to pins 10, 11, 12 (red, yellow, green).
2. Wire a push button to pin 2 with a 10kΩ pull-down resistor to GND.
3. Write the program with setup, loop, digital I/O, and conditional logic.
4. Upload and test. Verify button press triggers the crossing sequence.
5. Add a buzzer that sounds during the red phase (pedestrian walk signal).

**Expected Result:** Green LED on normally. Button press triggers yellow, then red (with buzzer), then returns to green.

**Troubleshooting:**
- LEDs don't light → Check pin numbers in code match wiring. Check LED polarity.
- Button has no effect → Check pull-down resistor connected to GND. Check button orientation.
- Sequence is erratic → Button bouncing. Add a small delay after detecting the press.

**Extension Challenge:** Add a second button for "emergency vehicle override." When pressed, all LEDs flash red rapidly for 5 seconds, then resume normal operation. Use a boolean flag to track emergency state.

### 8. Engineering Challenge
"Design a simple access control system for a school gate. The system has two buttons: 'Student' and 'Staff.' When 'Student' is pressed, a yellow LED blinks 3 times. When 'Staff' is pressed, a green LED stays on for 5 seconds. If BOTH are pressed simultaneously, a red LED lights (error — only one gate pass at a time). Write the logic and build the prototype."

### 9. Student Deliverable
- Working traffic-light controller with pedestrian button
- Arduino program with line-by-line comments
- Serial Monitor output showing button state changes
- Engineering notebook entry with program flowchart and pin assignment table

### 10. Assessment
- **Practical (50%):** Traffic light functions correctly; button responds reliably.
- **Code Quality (30%):** Proper structure, meaningful variable names, comments, correct use of setup/loop.
- **Quiz (20%):** Digital I/O concepts, pull-up/pull-down purpose, program structure.

### 11. Safety
- Arduino pins are 5V tolerant. Do not connect external power >5V to I/O pins.
- USB ports can supply limited current. If powering many LEDs, use external power.
- Always select the correct board and port before uploading.

### 12. STEM / Engineering Connection
Digital I/O is the foundation of all embedded systems — traffic lights, elevator controls, factory automation, ATM machines. In Kenya, microcontroller-based systems control railway signals, market security gates, and irrigation pumps. Understanding digital logic prepares students for PLC programming in industrial automation.

## WEEK 5 — Variables, Logic, Loops & Functions

### 1. Theme
Programming fundamentals: data, decisions, repetition, and modular code.

### 2. Learning Objectives
By the end of Week 5, students will be able to:
1. Declare and use variables with appropriate data types (int, float, boolean, long).
2. Write conditional statements (if, if-else, if-else-if) to make decisions based on sensor input.
3. Use for-loops and while-loops to repeat actions a specific number of times or until a condition is met.
4. Write and call custom functions to organize code into reusable blocks.
5. Use Serial Monitor for real-time debugging of program state.

### 3. Concepts & Theory

**Variables:** Named storage locations in memory. `int` stores whole numbers (-32,768 to 32,767). `float` stores decimal numbers. `boolean` stores true/false. `long` stores large whole numbers. `const` means the value never changes.

**Conditional Logic:**
- `if (condition) { ... }` — executes only if condition is true.
- `if (condition) { ... } else { ... }` — chooses between two paths.
- `if (condition1) { ... } else if (condition2) { ... }` — multiple conditions.
- Comparison operators: `==` (equal), `!=` (not equal), `<`, `>`, `<=`, `>=`.
- Logical operators: `&&` (AND), `||` (OR), `!` (NOT).

**Loops:**
- `for (init; condition; increment) { ... }` — repeats a known number of times.
- `while (condition) { ... }` — repeats while condition remains true.
- `delay(milliseconds)` pauses execution. Note: `delay()` blocks other code — advanced programs later use non-blocking timing.

**Functions:** Reusable blocks of code. They have a return type, name, parameters, and body. Functions make code readable, testable, and maintainable.

**Debugging with Serial:** `Serial.print()` and `Serial.println()` are the embedded programmer's best friends. Print variable values at key points to trace program execution.

## WEEK 6 — Analog Inputs, PWM, Sensors & Actuators

### 1. Theme
Controlling the analog world: reading continuous signals and producing variable outputs.

### 2. Learning Objectives
By the end of Week 6, students will be able to:
1. Explain Pulse Width Modulation (PWM) and how it simulates analog output on a digital pin.
2. Use `analogRead()` to read sensor values and `analogWrite()` to control LED brightness and motor speed.
3. Interface and calibrate an ultrasonic distance sensor (HC-SR04).
4. Control a servo motor to position a mechanical output precisely.
5. Build a responsive system combining sensor input and actuator output.

### 3. Concepts & Theory

**PWM (Pulse Width Modulation):** Digital pins can only be HIGH or LOW. PWM rapidly switches between HIGH and LOW at a fixed frequency, varying the duty cycle (percentage of time HIGH). The average voltage appears analog. `analogWrite(pin, value)` where value is 0–255. Arduino pins 3, 5, 6, 9, 10, 11 support PWM (marked with ~).

**Ultrasonic Sensor (HC-SR04):** Measures distance using sound. The Trig pin sends an ultrasonic pulse. The Echo pin receives the reflected pulse. Distance = (duration × 0.0343) / 2 (speed of sound ≈ 343 m/s; divide by 2 for round trip).

**Servo Motors:** Servos are position-controlled motors. They receive a PWM signal where pulse width determines angle (typically 1ms = 0°, 1.5ms = 90°, 2ms = 180°). The Arduino Servo library handles this automatically. `servo.write(angle)` sets position from 0 to 180.

**Sensor-Actuator Loop:** The fundamental control pattern: Read sensor → Process data → Command actuator → Repeat. This is the basis of all automation.

- Ruler or measuring tape

### 6. Instructor Teaching (20 minutes)

2. **analogRead/analogWrite (5 min):** Map potentiometer value (0–1023) to LED brightness (0–255) using `map()`.

- Readings fluctuate → Add averaging: take 3 readings and use the median.

## WEEK 7 — Motor Control, Motor Drivers & First Mobile Subsystem

### 1. Theme
Powering movement: DC motor control, motor drivers, and building the first mobile robot subsystem.

### 2. Learning Objectives
By the end of Week 7, students will be able to:
1. Explain why Arduino pins cannot directly power DC motors and why a motor driver is required.
2. Wire and control a DC motor using the L298N or L293D motor driver.
3. Program forward, backward, stop, and variable-speed motor control using PWM.
4. Build a single-motor drivetrain subsystem mounted on a temporary chassis.
5. Test and troubleshoot motor power, wiring, and control logic.

### 3. Concepts & Theory

**Why Motor Drivers?** DC motors draw high current (100mA–1A+) and produce electrical noise (back-EMF) that can damage microcontrollers. Arduino pins supply only 40mA — insufficient for motors. A motor driver is an H-bridge circuit that handles high current and protects the microcontroller.

**H-Bridge:** An electronic circuit that enables a motor to run forward or backward by switching the polarity of the voltage across it. It has four switches arranged in an "H" pattern. L298N and L293D are common H-bridge ICs.

**L298N Motor Driver:**
- OUT1, OUT2 → Motor terminals
- ENA → PWM speed control for Motor A
- IN1, IN2 → Direction control for Motor A
- 12V / VCC → Motor power supply (can use 9V battery or 4×AA)
- GND → Common ground (MUST connect to Arduino GND)
- 5V → Can power Arduino from driver (optional)

**Control Logic:**
- IN1=HIGH, IN2=LOW → Forward
- IN1=LOW, IN2=HIGH → Backward
- IN1=LOW, IN2=LOW → Stop (coast)
- IN1=HIGH, IN2=HIGH → Brake
- ENA PWM (0–255) → Speed control

**Power Systems:** Motors need more power than logic circuits. Always use a separate battery for motors if possible, with shared ground. Never power motors from Arduino 5V pin — it will overload and damage the board.

### 4. Components & Equipment
- Arduino Uno + USB cable
- Breadboard and jumper wires
- L298N motor driver module
- DC motor (3–6V, with gearbox preferred)
- Wheels (to fit motor shaft)
- 9V battery or 4×AA battery holder
- Battery snap/connector
- Multimeter
- Cardboard or acrylic for temporary chassis
- Double-sided tape or hot glue gun
- Laptop with Arduino IDE

### 5. Pre-Lab / Starter Activity (10 minutes)
**"Motor Power Math"**
Students calculate: A DC motor draws 200mA at 6V. How many Arduino pins (40mA each) would be needed to power it? (Answer: 5 pins, which is impossible and unsafe). This establishes why motor drivers exist before seeing the hardware.

### 6. Instructor Teaching (20 minutes)
1. **Motor Fundamentals (5 min):** How DC motors work (magnetic fields, commutator). Why they need drivers.
2. **H-Bridge Theory (5 min):** Draw the H-bridge. Show how switch combinations create forward/backward/stop.
3. **L298N Wiring (5 min):** Show the module. Explain each pin. Emphasize common ground.
4. **Power Safety (5 min):** Separate motor power from logic power. Fuse protection. Battery handling.

### 7. Hands-On Practical (50 minutes)

**Objective:** Build a single-motor "test rover" that drives forward for 2 seconds, stops, reverses for 2 seconds, and stops — controlled entirely by the Arduino.

**Materials:** Arduino, L298N, DC motor, wheel, battery, cardboard chassis, jumper wires.

**Procedure:**
1. Create a temporary chassis: Cut cardboard into a 15cm × 10cm base. Mount the motor at one end (drive wheel) and use a caster wheel or marble at the other end for balance.
2. Wire L298N: ENA→pin 9, IN1→pin 7, IN2→pin 8, OUT1/OUT2→motor, 12V→battery+, GND→battery- AND Arduino GND.
3. Write the program with motor control functions.
4. Upload and test on the floor. Observe movement.
5. Test variable speeds: Change speed to 128 (50%) and observe slower movement.

**Expected Result:** Rover drives forward, stops, reverses, stops in a repeating cycle. Motor speed responds to PWM values.

**Troubleshooting:**
- Motor doesn't run → Check battery voltage. Check common ground. Check IN1/IN2 wiring.
- Motor runs in one direction only → One direction pin not connected. Check solder joints on driver.
- Arduino resets when motor starts → Motor drawing too much current from shared supply. Use separate battery for motor.
- Rover spins in circles (when dual-motor later) → One motor wired backwards or different speeds.

**Extension Challenge:** Add the ultrasonic sensor from Week 6. Program the rover to drive forward until an obstacle is detected (<20cm), then reverse and turn. This is the first autonomous behavior — the foundation of the final robot.

- Never short motor terminals — sparks and battery damage can occur.

## WEEK 8 — Engineering Design Process & Robot Architecture

### 1. Theme
From idea to structure: applying systematic engineering design to robot chassis planning.

### 2. Learning Objectives
By the end of Week 8, students will be able to:
1. Describe and apply each step of the engineering design process to a robotics problem.
2. Generate and evaluate multiple design concepts for a robot chassis using weighted criteria.
3. Create dimensioned hand sketches of a robot chassis with labeled components and clearances.
4. Select appropriate materials for robot construction based on strength, weight, cost, and availability.
5. Plan the physical layout of electronics, sensors, motors, and power on a robot platform.

### 3. Concepts & Theory

**The Engineering Design Process:**
1. **Identify Problem:** What must the robot do? What are the constraints (size, weight, cost, time)?
2. **Research:** How do existing robots solve similar problems? What materials are available?
3. **Generate Ideas:** Brainstorm multiple solutions. No idea is too wild at this stage.
4. **Design:** Select the best idea. Create detailed sketches with dimensions. Consider manufacturability.
5. **Build:** Construct a prototype. Use available tools and materials.
6. **Test:** Does it meet requirements? Measure performance.
7. **Analyze Results:** What worked? What failed? Why?
8. **Improve:** Modify the design based on test results.
9. **Document:** Record the final design, changes made, and lessons learned.
10. **Present:** Communicate the solution to stakeholders.

**Robot Architecture:** The arrangement of subsystems on a mobile platform:
- **Chassis:** The structural frame that holds everything.
- **Drivetrain:** Motors, wheels, and transmission that enable movement.
- **Power System:** Batteries, regulators, and distribution.
- **Control System:** Microcontroller and wiring.
- **Sensor System:** Ultrasonic, IR, and other sensors positioned for optimal field of view.
- **Payload Area:** Space for carrying objects (for the final project).

**Design Constraints for the STEMForge Navigator:**
- Maximum dimensions: 20cm × 15cm × 10cm (fits on school desks)
- Maximum weight: 1kg (including batteries)
- Must carry a 200g payload
- Must accommodate: Arduino, L298N, 2× motors, ultrasonic sensor, 2× IR sensors, battery pack
- Must be buildable with hand tools and basic materials

**Material Selection:**
- **Cardboard:** Free, easy to cut, weak, absorbs moisture.
- **Acrylic/Plexiglass:** Strong, transparent, requires scoring or laser cutting.
- **Foam Board:** Lightweight, easy to cut, moderate strength.
- **3D-Printed PLA:** Custom shapes, requires printer access, slow.
- **Wood (plywood):** Strong, cheap, requires sawing and drilling.
- **Recycled materials:** Bottles, containers, CD cases — promotes creativity and sustainability.

## WEEK 9 — CAD Fundamentals & Chassis Design

### 1. Theme

### 2. Learning Objectives

4. Extrude 2D profiles into 3D parts and assemble multiple parts into a robot chassis model.
5. Export CAD models as STL files for 3D printing and as images for documentation.

### 3. Concepts & Theory

**What is CAD?** Computer-Aided Design software allows engineers to create precise digital models of physical objects. Unlike hand sketches, CAD models are dimensionally accurate, easily modified, and can be used directly for manufacturing (3D printing, CNC machining, laser cutting).

**CAD for Robotics:** In robot design, CAD is used to ensure all components fit together before building, calculate mass and center of gravity, plan wiring routes, create manufacturing files, and generate engineering drawings.

**Tinkercad (Recommended for STEMForge):**
- Free, browser-based, no installation required
- Intuitive drag-and-drop interface
- Built-in Arduino and electronics components
- Exports STL files directly
- Works on low-spec computers and tablets

**Basic CAD Operations:**
- **Sketch:** Draw 2D shapes on a plane.
- **Extrude:** Pull a 2D shape into 3D by a specified distance.
- **Hole:** Create voids by subtracting shapes (used for mounting holes, wire channels).
- **Align:** Position objects relative to each other.
- **Group:** Combine multiple shapes into one object.
- **Measure:** Check dimensions and distances.

**Design for Manufacturability (DFM):**
- Minimum wall thickness: 2mm for 3D printing
- Hole diameter should match screw/bolt size (e.g., 3mm hole for M3 screw)
- Avoid overhangs >45° without support
- Include fillets (rounded corners) to reduce stress concentration

## WEEK 10 — Prototyping, 3D Printing & Mechanical Assembly

### 1. Theme
From digital model to physical object: prototyping, additive manufacturing, and mechanical construction.

### 2. Learning Objectives
By the end of Week 10, students will be able to:
1. Explain how FDM 3D printing works and identify key print parameters (layer height, infill, support).
2. Prepare a CAD model for 3D printing by checking orientation, adding supports, and slicing.
3. Construct a robot chassis using a combination of 3D-printed parts, laser-cut parts, or hand-cut materials.
4. Assemble mechanical subsystems (motors, wheels, sensors) onto the chassis securely.
5. Test the mechanical integrity of the chassis and iterate based on physical findings.

### 3. Concepts & Theory

**3D Printing (FDM — Fused Deposition Modeling):**
- A nozzle heats plastic filament (usually PLA or ABS) to ~200°C.
- Molten plastic is extruded layer by layer onto a build plate.
- Each layer fuses to the one below it.
- Layer height determines resolution (0.1mm = fine, 0.3mm = fast).
- Infill percentage determines internal density (20% = lightweight, 80% = strong).
- Support material is added for overhangs >45° and bridges.

**3D Printing Workflow:** CAD model → STL file → Slicer software → Set parameters → Generate G-code → Send to printer → Monitor first layers → Remove print, clean supports.

**Laser Cutting:** A focused laser beam cuts through flat sheet material (acrylic, plywood, cardboard). Produces precise 2D profiles that slot together. Faster than 3D printing for flat parts.

**Hand Fabrication:**
- Cardboard: Cut with scissors or craft knife. Fold for rigidity.
- Acrylic: Score with knife and snap. Drill holes with hand drill.
- Wood: Saw, drill, sand. Requires more tools and safety precautions.

**Mechanical Assembly:**
- Use screws and nuts (M3 × 10mm) for secure, removable joints.
- Use hot glue for permanent, quick joints (not for high-stress areas).
- Use zip ties for cable management and light-duty holding.
- Ensure all moving parts have clearance (wheels must spin freely).

- Slicer software (Cura) on laptop
- Cardboard, acrylic, or plywood

## WEEK 11 — Obstacle Detection & Responsive Robot Behaviour

### 1. Theme
Giving the robot awareness: integrating sensors for real-world perception and response.

### 2. Learning Objectives
By the end of Week 11, students will be able to:
1. Integrate multiple sensors (ultrasonic and IR) onto the robot chassis with proper wiring.

3. Explain the difference between proactive (ultrasonic) and reactive (bump/contact) sensing.
4. Implement a simple obstacle-avoidance algorithm using conditional logic.
5. Test and calibrate sensor thresholds for reliable detection on different surfaces.

### 3. Concepts & Theory

**Sensor Integration:** Combining multiple sensors to give the robot a more complete picture of its environment. Each sensor has strengths and weaknesses:
- **Ultrasonic:** Good for distance, works in darkness, wide beam, slow update rate, poor with soft/angled surfaces.
- **IR Reflective:** Good for line detection, fast response, short range, affected by ambient light.
- **Contact/Bump:** Simple, reliable, but only detects after collision.

**Obstacle Avoidance Algorithm (Simple):**
```
Loop forever:
    Measure distance ahead
    If distance < threshold:
        Stop
        Back up slightly
        Turn
    Else:
        Drive forward
```

**Sensor Calibration:**
- Measure actual distances vs. sensor readings.
- Adjust for surface type (soft fabric absorbs ultrasound; hard walls reflect it).
- Set thresholds with margin (e.g., stop at 20cm, not 5cm, to allow reaction time).
- Test in the actual environment (school floor, walls, desks).

**Wiring Integration:**
- Plan wire routes to avoid tangling in wheels.
- Use color coding: red = 5V, black = GND, yellow = signal.
- Secure wires with zip ties or tape.
- Leave slack for movement but not so much that wires drag.

## WEEK 12 — Decision-Making, State Machines & Sensor Fusion

### 1. Theme
Intelligent behavior: programming the robot to make decisions using states and multiple sensor inputs.

### 2. Learning Objectives
By the end of Week 12, students will be able to:
1. Explain what a state machine is and how it organizes complex robot behavior into discrete states.
2. Implement a finite state machine in Arduino code using switch-case or if-else structures.
3. Combine data from multiple sensors (ultrasonic + IR) to make more robust navigation decisions.
4. Program the robot to follow a line using IR reflective sensors and a simple control algorithm.
5. Debug state-based programs using Serial Monitor to track state transitions.

### 3. Concepts & Theory

**Finite State Machines (FSM):** A mathematical model of computation where the robot can be in exactly one of a finite number of states at any time. Transitions between states are triggered by events (sensor readings, timers).

**States for the STEMForge Navigator:**
- `STATE_FORWARD` — Driving straight, monitoring sensors
- `STATE_AVOID` — Obstacle detected; executing avoidance maneuver
- `STATE_LINE_FOLLOW` — Following a line on the ground
- `STATE_LOST` — No line detected; searching for line
- `STATE_DELIVER` — At destination; stopped with payload ready

**State Machine Implementation:**
```cpp
enum RobotState { FORWARD, AVOID, LINE_FOLLOW, LOST, DELIVER };
RobotState currentState = FORWARD;

void loop() {
    switch (currentState) {
        case FORWARD:
            forward(speed);
            if (obstacleDetected()) currentState = AVOID;
            if (lineDetected()) currentState = LINE_FOLLOW;
            break;
        case AVOID:
            executeAvoidance();
            if (avoidanceComplete()) currentState = FORWARD;
            break;
        // ... etc
    }
}
```

**Sensor Fusion:** Combining data from multiple sensors to make better decisions than any single sensor could provide. For example:
- Ultrasonic says "clear ahead" but IR says "line ending" → Slow down, prepare to turn.
- Ultrasonic says "obstacle" but IR says "still on line" → Obstacle might be above the line (overhang); proceed with caution.

**Line Following:**
- IR sensor emits infrared light and measures reflected intensity.
- Black surfaces absorb IR; white surfaces reflect it.
- Two sensors: left and right of the line.
- If left sensor sees white, right sees black → drifted right, turn left.
- If right sensor sees white, left sees black → drifted left, turn right.
- If both see black → on the line, drive forward.
- If both see white → lost, search mode.

## WEEK 13 — Full Integration, Testing, Debugging & Optimization

### 1. Theme
Bringing it all together: integrating subsystems, systematic testing, and performance optimization.

### 2. Learning Objectives
By the end of Week 13, students will be able to:
1. Integrate all subsystems (electronics, software, sensors, motors, mechanics) into a single functioning robot.
2. Apply systematic debugging techniques to isolate and repair faults in an integrated system.
3. Optimize robot performance by adjusting parameters (speed, thresholds, timing) based on test data.
4. Conduct structured tests to evaluate reliability, consistency, and robustness.
5. Document test procedures, results, and modifications in the engineering notebook.

### 3. Concepts & Theory

**System Integration:** The process of combining independently developed subsystems into a complete system. Integration is where most projects fail — not because individual parts don't work, but because interfaces between parts are misunderstood.

**Integration Strategy — Bottom-Up:**
1. Test each subsystem independently (unit testing).
2. Integrate two subsystems and test (integration testing).
3. Add the next subsystem and test.
4. Continue until the complete system is assembled.

**Debugging Integrated Systems:**
- **Divide and Conquer:** Isolate the faulty subsystem. Does the motor work when controlled directly? Does the sensor read correctly when the motor is off?
- **Serial Debugging:** Print the state of all variables at each loop iteration.
- **Hardware Isolation:** Disconnect non-essential components to find interference.
- **Power Analysis:** Measure battery voltage under load. Motors cause voltage drops that can reset the Arduino.
- **Ground Loops:** Ensure all components share a common ground.

**Optimization Parameters:**
- **Motor speed:** Higher = faster but less control, more power drain.
- **Turn duration:** Affects turn angle; depends on surface and battery voltage.
- **Sensor threshold:** Affects sensitivity vs. false triggers.
- **Delay times:** Affects responsiveness vs. stability.
- **PWM values:** Balance straight-line driving by adjusting left/right motor speeds independently.

**Test Matrix:** A structured way to test all combinations of conditions:
| Test | Surface | Obstacle | Line | Expected Behavior | Pass/Fail |
|------|---------|----------|------|-------------------|-----------|
| 1 | Tile | None | Straight | Follow line | |
| 2 | Tile | Box | Straight | Avoid, return to line | |
| 3 | Carpet | None | Curve | Follow curve | |
| 4 | Carpet | Chair | Curve | Avoid, recover | |

2. **Gradual Integration (10 min):**
   - Connect motors + driver + Arduino. Test basic movement.
   - Add ultrasonic sensor. Test obstacle avoidance.
   - Add IR sensors. Test line following.
   - Add all components. Test state machine.
3. **Test Campaign (20 min):**
   - Run the test matrix (minimum 6 tests):
     - Test 1: Straight line, no obstacles, smooth floor
     - Test 2: Straight line, box obstacle
     - Test 3: Curved line, no obstacles
     - Test 4: Curved line, chair leg obstacle
     - Test 5: No line, open floor with obstacles
     - Test 6: Full course with line + multiple obstacles
   - For each test: Record time to complete, number of failures, recovery success.
   - Note any unexpected behavior.
4. **Optimization (10 min):**
   - Based on test data, adjust ONE parameter:
     - If robot turns too far → reduce turn duration.
     - If robot misses obstacles → lower ultrasonic threshold.
     - If robot drifts on straight line → adjust left/right motor PWM balance.
     - If robot is too slow → increase base speed.
   - Re-run the worst-performing test. Verify improvement.

**Expected Result:** A fully integrated robot that completes the test course reliably. Test matrix is complete with data. At least one parameter has been optimized with before/after comparison.

**Troubleshooting:**
- Arduino resets during motor operation → Battery voltage drops. Use fresh batteries or separate power.
- Sensors give erratic readings when motors run → Electrical noise. Add capacitors across motor terminals or separate power supplies.
- Robot behaves differently after integration → Pin conflict. Check that no two functions use the same pin.
- Program uploads but doesn't run → Memory overflow. Reduce string literals or use F() macro for Serial.print.
- One test always fails → That condition reveals a design flaw. Document it and attempt a fix.

**Extension Challenge:** Implement a "watchdog timer" — if the robot is in the same state for more than 10 seconds without progress, it automatically resets to FORWARD state. This prevents infinite loops in real-world operation.

### 8. Engineering Challenge
"A factory robot must operate 8 hours without failure. Design a reliability test plan: what would you test, how many times, and what metrics would you use? Apply a simplified version to your robot: run it through your test course 10 times and calculate a 'reliability score' = (successful completions / total attempts) x 100%. Identify the most common failure mode and engineer a fix."

### 9. Student Deliverable
- Fully integrated and tested robot
- Completed test matrix with data for at least 6 tests
- Optimization log: parameter changed, before value, after value, improvement measured
- Updated Arduino program (final pre-showcase version)
- Engineering notebook entry with integration notes, test data tables, and failure analysis

### 10. Assessment
- **Integration (30%):** All subsystems work together; no loose connections; clean wiring.
- **Test Campaign (30%):** Test matrix is complete; data is recorded; tests are appropriate.
- **Optimization (20%):** At least one parameter improved with quantitative evidence.
- **Debugging (20%):** At least one integration fault was identified, diagnosed, and repaired.

### 11. Safety
- Integrated robots have more power and more ways to fail. Maintain a clear test area.
- Be prepared for sudden movements. Keep the power switch or battery connector accessible for emergency disconnect.
- Repeated motor operation drains batteries. Monitor battery temperature.
- If using LiPo batteries (advanced teams), never leave charging unattended. Use fire-safe bags.

### 12. STEM / Engineering Connection
System integration and testing are where engineering projects succeed or fail. NASA conducts thousands of integration tests before a rocket launches. Kenyan infrastructure projects (roads, railways, power grids) require extensive integration testing of electrical, mechanical, and control systems. The discipline of structured testing and optimization separates amateur projects from professional engineering.

# 7. FINAL ROBOT PROJECT

## The STEMForge Navigator

### Project Description
The STEMForge Navigator is an autonomous campus-assistant robot designed to navigate indoor environments, avoid obstacles, follow marked paths, and deliver small payloads. It represents a complete integration of electronics, software, sensors, and mechanical design — the culmination of 14 weeks of progressive learning.

### Final Robot Specifications
- **Dimensions:** 180mm x 130mm x 100mm (L x W x H)
- **Weight:** 600–800g (including batteries)
- **Payload Capacity:** 200g
- **Power:** 4xAA NiMH rechargeable batteries (motor power) + 9V or USB (Arduino logic)
- **Microcontroller:** Arduino Uno
- **Motor System:** 2x DC motors with gearbox + L298N dual H-bridge driver
- **Sensors:** 1x HC-SR04 ultrasonic (forward obstacle detection), 2x IR reflective (line following)
- **Locomotion:** Differential drive (two powered wheels, one caster/skid)
- **Chassis:** Student-designed and fabricated (3D-printed, laser-cut, or hand-built)
- **Software:** State-machine-based autonomous navigation with obstacle avoidance, line following, and lost-robot recovery

### Why This Project?
1. **Achievable:** Every subsystem has been built and tested individually before integration. No single week is overwhelming.
2. **Comprehensive:** Covers all 12 target competencies.
3. **Relevant:** Campus delivery, agricultural transport, and warehouse automation are growing needs in Kenya.
4. **Scalable:** Students can add features (Bluetooth control, camera, GPS) in advanced programs.
5. **Visible Success:** Even a basic Navigator that drives and avoids obstacles is impressive and motivating.

### Project Subsystems Developed Across the Term
| Phase | Weeks | Subsystem | Integration Point |
|-------|-------|-----------|-------------------|
| Electronics | 1–3 | Power, LEDs, sensors, voltage dividers | Sensor circuits feed into Arduino |
| Programming | 4–7 | Arduino code, motor control, servo, ultrasonic | Controls all hardware |
| Mechanical | 8–10 | Chassis design, CAD, fabrication, assembly | Houses and protects all components |
| Autonomy | 11–14 | State machine, sensor fusion, line follow, obstacle avoid | Combines all previous subsystems |

# 9. ENGINEERING NOTEBOOK FRAMEWORK

## Purpose
The engineering notebook is the primary record of the student's engineering process. It is evidence of thinking, designing, building, testing, failing, and improving. In professional engineering, notebooks are legal documents used for patent applications and dispute resolution.

## Notebook Requirements
- **Format:** A4 hardcover or spiral-bound notebook with numbered pages
- **Ownership:** One notebook per student (not per team)
- **Permanence:** Use pen (not pencil). Cross out mistakes with a single line — do not erase.
- **Dating:** Every entry must be dated.
- **Witnessing:** Major design decisions should be signed and dated by a peer or facilitator.

## Weekly Notebook Structure

### For Every Week, Students Must Record:

1. **Date and Week Number**
2. **Learning Objectives:** Copy from curriculum
3. **Concept Notes:** Key theory in student's own words
4. **Design Sketches:** Hand-drawn diagrams of circuits, code flowcharts, or mechanical designs
5. **Component List:** What was used, with values and part numbers where known
6. **Procedure Summary:** What was done, in the student's own words (not copied from curriculum)
7. **Code/Calculations:** Key code snippets or mathematical working
8. **Test Data:** Measurements, observations, Serial Monitor outputs
9. **Failures and Fixes:** What went wrong, hypothesis for why, what was tried, final solution
10. **Reflection:** What was learned, what was surprising, what would be done differently

### Specific Week Requirements

| Week | Specific Notebook Content |
|------|--------------------------|
| 1 | Ohm's Law calculations; resistor color code chart; first circuit diagram |
| 2 | Series/parallel calculations; multimeter readings table; troubleshooting log |
| 3 | Voltage divider calculation; LDR calibration table; first Arduino code with annotations |
| 4 | Pin assignment table; program flowchart; traffic light timing diagram |
| 5 | Variable table; function documentation; game logic explanation |
| 6 | Distance calculation; servo angle mapping; sensor wiring diagram |
| 7 | Motor driver wiring diagram; power calculations; chassis material test |
| 8 | Three concept sketches; decision matrix; final dimensioned drawing |
| 9 | CAD screenshots (3 views); STL export confirmation; dimension verification |
| 10 | Fabrication photos; assembly sequence; mechanical test observations |
| 11 | Integrated wiring diagram; obstacle avoidance algorithm; calibration table |
| 12 | State diagram; IR calibration data; sensor fusion truth table |
| 13 | Test matrix with data; optimization log; integration fault analysis |
| 14 | Challenge course results; presentation notes; final reflection (1 page) |

## Notebook Assessment Checklist
- [ ] All 14 weeks have dated entries
- [ ] Every practical has a circuit diagram or mechanical sketch
- [ ] All code is commented and explained
- [ ] Failures are documented honestly (not hidden)
- [ ] Test data is presented in tables
- [ ] Reflections are specific, not generic ("I learned a lot")
- [ ] Notebook is organized with a table of contents
- [ ] No pages are torn out or heavily blacked out

- [ ] Set up the demonstration area
- [ ] Lay out safety equipment

### Expected Setup Time
- 15–20 minutes for component distribution and kit checks
- 5 minutes for laptop boot and Arduino IDE launch
- 10 minutes for attendance and recap

## During Sessions

### Teaching Strategy
1. **Hook (5 min):** Starter activity that connects to real life and creates curiosity.
2. **Concept (15 min):** Explain theory using analogies, diagrams, and live demos. Ask questions constantly.
3. **Model (10 min):** Demonstrate the practical activity. Think aloud so students hear the reasoning.
4. **Guided Practice (15 min):** Students build with facilitator circulating. Ask "What do you think will happen?" before they test.
5. **Independent Challenge (15 min):** Engineering challenge. Facilitator provides hints, not answers.
6. **Reflection (5 min):** What failed? What worked? What would you change?

### Demonstration Best Practices
- Use a document camera or large components so all students can see
- Build circuits slowly; explain each connection
- Make deliberate mistakes and model debugging aloud
- Use the Serial Monitor live so students see real data
- Keep demos under 10 minutes; students learn by doing, not watching

### Guided Practice
- Circulate constantly. Look for common errors.
- When a student is stuck, ask: "What have you tried? What did you expect? What happened instead?"
- Never take over a student's build. Guide with questions.
- Celebrate failures: "Excellent — you just learned something that doesn't work. That's engineering."

### Independent Challenge
- Set clear deliverables and time limits
- Encourage teams to compete constructively
- For advanced students: provide the expert challenge immediately
- For struggling students: break the challenge into smaller steps

### Troubleshooting During Sessions
- Maintain a "debugging station" with multimeter, spare components, and a working reference circuit
- Common issues and quick checks:
  - Nothing works: Check power, check ground, check USB connection
  - LED doesn't light: Check polarity, check resistor, check pin number
  - Motor doesn't run: Check battery voltage, check L298N enable, check wiring
  - Sensor reads wrong: Check wiring, check threshold, check Serial Monitor
  - Code won't upload: Check board selection, check port, check for syntax errors

## After Sessions

### Assessment (15 minutes after session)
- Grade practical work using the weekly rubric
- Note students who need extra support next week
- Record attendance and participation

### Equipment Recovery (15 minutes)
- Collect all components into kits
- Check for missing items
- Test and charge batteries
- Store kits in locked cabinet
- Note any damaged components for replacement

### Documentation
- Update student progress tracker
- Photograph notable student work for portfolio
- Write brief session notes: what worked, what didn't, adjustments for next time

### Student Progress Tracking
Maintain a simple spreadsheet with:
- Student name
- Week-by-week practical scores
- Quiz scores
- Notebook check scores
- Attendance
- Facilitator notes (strengths, concerns)

# 13. DIFFERENTIATION STRATEGY

## Philosophy
All students can succeed, but not at the same pace or in the same way. Differentiation ensures every student is appropriately challenged — neither bored nor overwhelmed.

## Differentiation by Task

### For Each Major Practical, Provide Three Levels:

#### Core Challenge
**For:** Students new to electronics and programming.  
**Characteristics:** Step-by-step guidance with clear targets. Focus on building confidence and foundational skills.  
**Support:** Facilitator checks understanding frequently. Peer support from advanced students. Reference sheets available.

#### Advanced Challenge
**For:** Students progressing faster than the core pace.  
**Characteristics:** Open-ended problem with multiple valid solutions. Requires application of concepts in new contexts.  
**Support:** Facilitator provides hints, not solutions. Encourages independent research. Peer collaboration.

#### Expert / Extension Challenge
**For:** Highly capable students who complete core and advanced work quickly.  
**Characteristics:** Introduces meaningful engineering complexity: additional sensors, algorithmic thinking, design constraints.

# 14. SAFETY FRAMEWORK

## Electrical Safety
- **Voltage Limits:** Students work only with low-voltage DC (5V–9V). Never exceed 12V.
- **Battery Safety:**
  - Never short-circuit batteries. Use a fuse if possible.
  - Remove batteries from holders when storing kits.
  - Do not mix old and new batteries.
  - If using LiPo batteries (expert teams only), never leave charging unattended. Use fire-safe bags.
- **Component Handling:**
  - Do not touch exposed metal when power is connected.
  - Always disconnect power before changing circuit configuration.
  - Report damaged components (frayed wires, cracked batteries) immediately.
- **Arduino Safety:**
  - I/O pins are 5V tolerant. Do not connect >5V to any pin.
  - Do not power motors from Arduino 5V pin.
  - USB ports can supply limited current. External power for motors is mandatory.

## Mechanical & Tool Safety
- **Craft Knives:**
  - Always cut away from the body.
  - Use cutting mats.
  - Replace dull blades — they slip.
  - Never attempt to catch a falling knife.
- **Hot Glue Guns:**
  - Nozzle reaches 150°C+. Never touch.
  - Use stands, not cups or paper.
  - Allow 5 minutes to cool before handling glued joints.
- **Drills:**
  - Secure workpiece with clamps.
  - Wear safety glasses.
  - Do not wear loose clothing or jewelry.
- **3D Printers:**
  - Nozzle operates at 200°C+. Never touch.
  - Keep flammable materials away from printer.
  - Do not leave printing unattended for >30 minutes.
- **General Workshop:**
  - Tie back long hair.
  - No loose clothing near moving parts.
  - Wear closed-toe shoes.
  - Keep workspace organized.

## Battery Safety Protocol
1. Inspect batteries before each session for swelling, leakage, or damage.
2. Use the correct battery type for each application.
3. Store batteries in a cool, dry place.
4. Dispose of damaged batteries properly (do not throw in regular trash).
5. If a battery overheats or smokes: disconnect immediately, move to a safe area, and notify the facilitator.

## Emergency Procedures
- **Fire:** Use CO2 extinguisher for electrical fires. Never use water. Evacuate if fire spreads.
- **Burn:** Cool under running water for 10 minutes. Do not apply ice. Cover with clean cloth. Seek medical attention for severe burns.
- **Cut:** Apply pressure with clean cloth. Elevate if possible. Seek medical attention for deep cuts.
- **Electric Shock:** Disconnect power. Do not touch the person if they are still in contact with live electricity. Call for help immediately.

## Safety Assessment
- Week 1: Safety quiz (must pass to use tools)
- Week 5: Mid-term safety review
- Week 10: Tool safety practical assessment
- Week 14: Final safety observation during showcase

```cpp
// Motor control functions for L298N
const int enA = 9, in1 = 7, in2 = 8;   // Left motor
const int enB = 10, in3 = 12, in4 = 13; // Right motor

void setup() {
  pinMode(enA, OUTPUT); pinMode(in1, OUTPUT); pinMode(in2, OUTPUT);
  pinMode(enB, OUTPUT); pinMode(in3, OUTPUT); pinMode(in4, OUTPUT);
}

void forward(int speed) {
  analogWrite(enA, speed); digitalWrite(in1, HIGH); digitalWrite(in2, LOW);
  analogWrite(enB, speed); digitalWrite(in3, HIGH); digitalWrite(in4, LOW);
}

void reverse(int speed) {
  analogWrite(enA, speed); digitalWrite(in1, LOW); digitalWrite(in2, HIGH);
  analogWrite(enB, speed); digitalWrite(in3, LOW); digitalWrite(in4, HIGH);
}

void turnLeft(int speed) {
  analogWrite(enA, speed); digitalWrite(in1, LOW); digitalWrite(in2, HIGH);
  analogWrite(enB, speed); digitalWrite(in3, HIGH); digitalWrite(in4, LOW);
}

void turnRight(int speed) {
  analogWrite(enA, speed); digitalWrite(in1, HIGH); digitalWrite(in2, LOW);
  analogWrite(enB, speed); digitalWrite(in3, LOW); digitalWrite(in4, HIGH);
}

void stopMotors() {
  analogWrite(enA, 0); digitalWrite(in1, LOW); digitalWrite(in2, LOW);
```

## Template 3: Ultrasonic Distance Reading
```cpp
const int trigPin = 7;
const int echoPin = 6;

float readDistance() {
  digitalWrite(trigPin, LOW);
  delayMicroseconds(2);
  digitalWrite(trigPin, HIGH);
  delayMicroseconds(10);
  digitalWrite(trigPin, LOW);

  long duration = pulseIn(echoPin, HIGH, 30000); // 30ms timeout
  float distance = (duration * 0.0343) / 2;

  if (duration == 0) return -1; // Timeout = no echo
  return distance;
}
```

## Template 4: State Machine Structure
```cpp
enum RobotState { FORWARD, AVOID, LINE_FOLLOW, LOST };
RobotState currentState = FORWARD;

void loop() {
  switch (currentState) {
    case FORWARD:
      // Forward behavior
      if (obstacleDetected()) currentState = AVOID;
      break;

    case AVOID:
      // Avoidance behavior
      if (avoidanceComplete()) currentState = FORWARD;
      break;

    case LINE_FOLLOW:
      // Line following behavior
      if (lineLost()) currentState = LOST;
      break;

    case LOST:
      // Search behavior
      if (lineFound()) currentState = LINE_FOLLOW;
      break;
  }
}
```
